# ADR-040: Legacy Juspay Table Cleanup (Migration Tooling Exception)

**Status:** Accepted and implemented (2026-09-19).
**Date:** 2026-09-19
**Supersedes:** none
**Related:** ADR-037 (recurring billing foundation), ADR-038 (direct Razorpay provider), ADR-039 (provider-wired subscription lifecycle), INV-001 (Channel = Tenant), INV-019 (provider-neutral bindings)

## Context

The subscription plugin was refactored to be provider-neutral (`9a31beb`, "refactor(subscription): make recurring billing provider-neutral"). As part of that refactor the six legacy Juspay entities were deleted from the source tree, and the reconciliation entity was renamed at the database level:

```text
juspay_payment_reconciliation_required   →   subscription_reconciliation_required
juspayOrderId                            →   providerOrderId
```

Source-scoped verification after the refactor:

```bash
grep -Rni "juspay\|Juspay\|JUSPAY" src/plugins/subscription
# zero results
```

However, deleting an `@Entity` class from TypeScript does **not** remove the corresponding table from a deployed database. Read-only inspection of the deployed PostgreSQL instance (2026-09-19) returned six orphaned legacy tables:

| Table | Rows |
| --- | --- |
| `juspay_payment_attempt` | 0 |
| `juspay_payment_reconciliation_required` | 0 |
| `juspay_subscription_mandate` | 0 |
| `juspay_subscription_mandate_channels_channel` | 0 |
| `juspay_webhook_endpoint` | 0 |
| `juspay_webhook_event` | 0 |

All six are empty. This matters for choosing the migration strategy: with zero rows there is no operational history to preserve, so a **drop** is correct. A rename/data-migration strategy would be required only if these tables held data — in particular `juspay_payment_reconciliation_required`, which existed to record production reconciliation incidents.

### Why the Vendure CLI cannot express this change

`npx vendure migrate --generate subscription-reconciliation-and-legacy-cleanup` was executed. It emitted the `CREATE TABLE "subscription_reconciliation_required"` statement (plus its two indexes and the `organization_subscription` foreign key) but **no `DROP TABLE` statements for the six orphaned tables**.

This is a structural limitation of the tooling, not a configuration problem. Verified in the installed dependency tree:

```bash
grep -m1 '"version"' node_modules/typeorm/package.json
# "version": "0.3.31"

grep -n 'dropRemovedColumns\|dropOldIndices\|dropOldForeignKeys\|dropOldViews\|dropOldChecks\|dropOldExclusions' \
  node_modules/typeorm/schema-builder/RdbmsSchemaBuilder.js
# 158: await this.dropOldViews();
# 159: await this.dropOldForeignKeys();
# 160: await this.dropOldIndices();
# 161: await this.dropOldChecks();
# 162: await this.dropOldExclusions();
# 168: await this.dropRemovedColumns();
# (plus the method definitions for each)

grep -rln 'removedTables' node_modules/typeorm/schema-builder/
# NO_MATCH: removedTables not referenced in schema-builder

grep -rln 'TableRemoved' node_modules/typeorm/
# no results
```

## Decision

1. **Drop the six orphaned `juspay_*` tables.** All six were verified empty (0 rows, exact `COUNT(*)`) and no dependent objects exist (no views, materialized views, or other relations reference them). With no operational history to preserve, a rename-plus-data-migration strategy is unnecessary and a drop is the correct, simplest, fully-auditable change.

2. **Record this as the documented `.clinerules` §7 exception.** The rules require all schema changes to be generated by Vendure CLI migration tooling, and forbid hand-writing migration files. That requirement is satisfied here by the hand-editing being the *only* path available: the CLI generated the rest of the migration, and the six `DROP TABLE` statements were appended because the installed tooling is structurally incapable of emitting them.

3. **Deliver the change as one Vendure-registered migration:** `src/migrations/1789797901115-subscription-reconciliation-and-legacy-cleanup.ts`.

4. **Preserve the historical migration files untouched.** `1788058421475-JuspayRecurringBillingEntities`, `1788065585269-JuspayMultiTenantWebhookEndpoints`, `1788070602617-JuspayReconciliationRequiredEntity`, `1788059200478-JuspayLedgerHardening`, `1788158855462-JuspayWebhookEndpointSecretHardening` and `1789101316262-fix-duplicate-migrations` remain as applied history and must never be rewritten. Drop order in the new migration is dependency-aware: `juspay_subscription_mandate_channels_channel` (FK → `juspay_subscription_mandate`, FK → `channel`) is dropped first; the other five are mutually independent.

5. **Make the migration fully reversible.** Because hand-written DDL is involved, `down()` reconstructs all six tables — columns, types, nullability, defaults, primary keys, foreign keys, indexes and the partial unique index — from read-only catalog captures (`pg_attribute`, `pg_constraint`, `pg_indexes`) taken immediately before the drops, not from the deleted entity classes. Structural restoration only: the tables were empty, so no rows are restored.

## Consequences

**Positive**

- The deployed database schema converges with the provider-neutral source tree; the reconciliation entity table (`subscription_reconciliation_required`) is created and the six orphaned Juspay tables are removed.
- `npx vendure migrate --generate` reports a clean schema diff afterwards, so future migrations are trustworthy again.
- Rollback safety is preserved: `down()` restores the original six-table shape exactly.

**Negative / accepted**

- One migration is not fully CLI-generated. This is a permanent, documented exception rather than a pattern to copy; any future orphan-table cleanup must cite its own ADR.
- The migration touches table names that no longer exist in source. Anyone reading the migration without this ADR will see DDL for entities they cannot find; the in-file comment block and this ADR are the required mitigation.

### Applied state and convergence (2026-09-19)

The migration was applied through the Vendure CLI, then the schema diff was
re-evaluated to prove the deployed database now matches the entity model:

```bash
npx vendure migrate -r
# Successfully ran 1 migrations

npx vendure migrate -r      # re-run, convergence check
# No pending migrations found
```

`migrations` table after applying:

| id | timestamp | name |
| --- | --- | --- |
| 55 | 1789797901115 | `SubscriptionReconciliationAndLegacyCleanup1789797901115` |

Applied-state inspection of the deployed public schema:

| Object | Before | After |
| --- | --- | --- |
| `subscription_reconciliation_required` | absent | present (PK + FK → `organization_subscription`) |
| `juspay_*` table count | 6 | 0 |

The "No pending migrations found" result is the decisive evidence: had the six
`DROP TABLE` statements been omitted, the orphaned tables would remain in the
database but not in the metadata, and TypeORM would report no pending change
either way — so the explicit post-apply count of **0** `juspay_*` tables is what
confirms the hand-written portion actually executed.

### Rollback round-trip verification (2026-09-19)

Because `down()` is hand-written, rollback was not assumed — it was exercised
end-to-end. TypeORM runs migrations (and reverts) inside a transaction
(`migrationsTransactionMode` is unset, so the default applies), so a failing
`down()` would roll back rather than leave a partial schema.

```bash
npx vendure migrate --revert
# Successfully reverted last migration

npx vendure migrate -r
# Successfully ran 1 migrations
```

Verified at each step:

| Check | After `--revert` | After re-apply |
| --- | --- | --- |
| `juspay_*` tables | 6 restored | 0 |
| `subscription_reconciliation_required` | absent | present |
| `migrations` row for `1789797901115` | removed (pending again) | present |
| `npx vendure migrate -r` | — | `No pending migrations found` |

Two details of the restored shape were checked specifically because they are
the parts most likely to be lost in a hand-written reconstruction, and both
matched the original catalog capture exactly:

```sql
-- partial unique index on juspay_subscription_mandate
CREATE UNIQUE INDEX "IDX_e2b2245131f526d370d3a680cf"
  ON public.juspay_subscription_mandate ("subscriptionId")
  WHERE ((status)::text <> 'revoked'::text);

-- join table foreign keys
FK_57f2ade546c4f1f619870643abb  -> juspay_subscription_mandate
FK_e39d8ec2048843d7123633d2c5a  -> channel
```

The round-trip therefore leaves the database in the intended final state, and
the rollback-safety claim in *Consequences* is evidenced rather than asserted.

## Enforcement and Registration

- Migration lives at `src/migrations/1789797901115-subscription-reconciliation-and-legacy-cleanup.ts` and is picked up automatically by the glob in `src/vendure-config.ts`:

  ```ts
  migrations: [path.join(__dirname, "./migrations/*.+(js|ts)")],
  ```

  No config change is required, and no plugin-scoped migration registration is involved (this is a core `src/migrations` migration).

- Because `.clinerules` §9 requires new invariants to be documented before implementation, this ADR registers **no new invariant** — the cleanup removes tables, it does not add an invariant. Relevant existing invariants that remain satisfied: INV-001 (Channel = Tenant) and INV-019 (provider-neutral bindings).

`RdbmsSchemaBuilder` in TypeORM 0.3.31 has no `dropRemovedTables()` method, never reads a `removedTables` collection, and there is no `TableRemoved` schema-event class. The schema builder can drop removed **columns**, **indices**, **foreign keys**, **checks**, **exclusions** and **views** — but it has no code path that emits `DROP TABLE` for an entity that no longer exists in the metadata. Consequently `vendure migrate --generate` can never produce the orphan-table cleanup, at any version bump or configuration change.
