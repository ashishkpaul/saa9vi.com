# G1 — Tenant Hostname Contract: Inspection & Architectural Decision

> **Status:** Decision record (Gate G1 of `integration-gaps-worklist.md`)
> **Date:** 2026-09-15
> **Scope:** Inspection/decision only. No DB mutations, no Redis fixture manipulation, no schema migration performed or required.
>
> **⚠️ Historical snapshot:** Sections 1–4 record the repository state **as inspected before B-2 implementation (2026-09-15)**. B-2 subsequently implemented the accepted contract — see **Post-B-2 implementation status** at the end of this document.

## 1. Current code path (verified)

`TenantRegistrationService.registerNewTenant()` (Shop API, via `TenantShopResolver`):

```text
PENDING registration log (persist-first)
→ Seller
→ Channel (token auto-generated by Vendure)
→ Role (channel-scoped admin)
→ Administrator (UNVERIFIED + verification token + AccountRegistrationEvent)
→ TenantProfile.create({ channelId, businessName, contactEmail, timezone })
→ autoProvisionChannelResources (shipping/payment/stock)
```

Key facts verified in code:

* `TenantProfile.customDomain` is `nullable, unique` and is **NOT set at registration** — registration passes only `businessName/contactEmail/timezone` (`tenant-registration.service.ts` step 5).
* No `academySlug` is persisted at registration. The marketplace projection derives `academySlug` from **`BbbOrganization.slug`** (`MarketplaceIndexerService` BUG-023 fix), a separate entity created via `BbbOrganizationService` — a newly registered tenant has no `BbbOrganization`, so its marketplace docs would carry `academySlug: ''`.
* `TenantProfileService.create()/update()` already syncs `customDomain → Redis` via `DomainChannelResolverService.setMapping()` (key `channel-token:{domain}` → `Channel.token`, 7-day TTL refreshed on update; remove+set on change).

## 2. Current deployment path (verified)

* **Backend ingress:** `domainChannelMiddleware` (Express) resolves `req.hostname` against Redis (`channel-token:` prefix) and sets `X-Vendure-Token`; non-blocking fail-through to default channel.
* **Storefront ingress:** Next.js `GET /api/resolve-channel?hostname=` resolves the same Redis prefix and **always** returns `x-saa9vi-channel-token` (real token or `''`).
* **Caddy** (`nextjs-starter-vendure/deploy/Caddyfile`): `forward_auth` → `copy_headers x-saa9vi-channel-token` (Set/overwrite — client-supplied header cannot survive). Site addresses are currently **static placeholders** (`academy-a.example.com, academy-b.example.com`) with an explicit pointer to wildcard/on-demand TLS for dynamic provisioning. `marketplace.saa9vi.com` bypasses resolution.
* Prefix compatibility verified: backend middleware, `DomainChannelResolverService`, and storefront `resolve-channel` all use `channel-token:`.

## 3. Authoritative identity source

**`Channel.token` is the single authoritative tenant identity token.** Both resolution consumers (Vendure `X-Vendure-Token` and Next.js `x-saa9vi-channel-token`) derive from the **same Redis map**, written **only** by `DomainChannelResolverService` (triggered by `TenantProfileService`). No second mapping exists today; none may be introduced.

## 4. Gap

A newly registered tenant is **unreachable**: registration sets neither `customDomain` nor any platform hostname, so nothing seeds Redis, Caddy has no matching site block, and `resolve-channel` returns `''` → storefront falls back to the default channel (audit B-6). Additionally, the marketplace's `academySlug` (from `BbbOrganization.slug`) is unrelated to `TenantProfile`, so hostname derivation would have two candidate slug sources unless unified.

## 5. Candidate hostname contract — **DECIDED**

```text
Platform subdomain:  {tenantSlug}.saa9vi.com
Custom domain:       TenantProfile.customDomain (explicitly configured, existing flow)
```

* `{tenantSlug}` is a **new derived, unique, immutable** field persisted on `TenantProfile` (slugified from `businessName`, uniqueness-enforced). It is the single slug source of truth for hostnames.
* `BbbOrganization.slug` (marketplace display) must be **set from the same tenantSlug** at org creation/sync so marketplace `academySlug` and hostname never diverge. (Reconciliation of pre-existing orgs is a one-off B-2 task item.)
* `customDomain` remains reserved for explicitly configured domains and continues to use the existing `TenantProfileService` Redis sync unchanged.

## 6. Impact on Redis mapping

* Registration (B-2) must call `DomainChannelResolverService.setMapping('{tenantSlug}.saa9vi.com', channel.token)` — the **existing** mechanism, same prefix, same TTL/refresh semantics. No new mapping store, no second resolution mechanism.
* Subdomain mappings and customDomain mappings coexist in one map; deletion/teardown must remove both (`removeMapping`).
* Note the 7-day TTL: refreshed on profile update. **Re-affirmation was explicitly deferred from B-2** (amended 2026-09-15 during implementation): registration seeds the mapping, and `TenantProfileService.ensureTenantHostnameMapping()` (invoked on every `TenantProfileService.update()` save — not on arbitrary repository-level saves elsewhere) provides update-path recovery — but the scheduled re-affirmation/reconciliation strategy for idle tenants is a **separate operational decision**, tracked in `integration-gaps-worklist.md`, not a B-2 deliverable.

## 7. Impact on Caddy/TLS

* The static site block must become a **wildcard** site (`*.saa9vi.com`) with **on-demand TLS**, proxying through the same `forward_auth` flow — Caddy config only; no code change. `marketplace.saa9vi.com` stays a separate block (no resolution).
* Wildcard cert requires DNS provider automation (`dns_*` plugin) for `*.saa9vi.com`; deployment-level work tracked under G10, not B-2.

## 8. Impact on Next.js resolve-channel

**None required.** `resolve-channel` is hostname-agnostic against the Redis map; subdomains resolve identically to custom domains. B-6 (production fail-closed instead of default-channel fallback) remains a separate deferred task.

## 9. Impact on custom domains

None — the existing `customDomain` create/update/delete Redis sync is preserved as-is. Custom domains ride the same map and the same Caddy on-demand-TLS flow (with per-tenant CA validation in production, G10).

## 10. Architectural decision

**ACCEPTED (this record):** the platform hostname contract is `{tenantSlug}.saa9vi.com`, derived from a new unique `TenantProfile.tenantSlug`, seeded into the **existing** `DomainChannelResolverService` Redis map at registration; `customDomain` continues as the explicit-configuration override; `BbbOrganization.slug` is synchronized from `tenantSlug` (not independent). There is exactly **one** hostname→channel resolution mechanism (Redis `channel-token:` map) and exactly **one** writer (`DomainChannelResolverService`). This satisfies INV-001 (Channel = tenant identity) and keeps channel resolution out of template/storefront code.

## 11. B-2 authorization

**AUTHORIZED**, scoped as:

1. Add unique `TenantProfile.tenantSlug` via **Vendure CLI migration** (`npx vendure migrate`).
2. Derive + persist `tenantSlug` at registration (slugified `businessName`, uniqueness retry) and seed the subdomain Redis mapping via `DomainChannelResolverService`.
3. Sync `BbbOrganization.slug` from `tenantSlug` (org auto-provision or reconciliation step).
4. Registration acceptance test: Tenant A/B via GraphQL → `channel-token:{slug}.saa9vi.com` present in Redis → `resolve-channel?hostname=` returns the correct tokens. No manual Redis/DB writes.
5. ~~Mapping-TTL re-affirmation strategy decided during B-2.~~ **Amended 2026-09-15:** TTL re-affirmation was explicitly deferred from B-2 and is tracked as a separate operational decision (see the TTL note above). B-2 delivers the registration seed plus update-path recovery only.
6. Caddy wildcard/on-demand TLS and B-6 fail-closed behavior are explicitly **out of B-2 scope** (G10 / B-6).

## 12. Post-B-2 implementation status (2026-09-15)

B-2 was implemented and accepted after this decision record was written:

* `TenantProfile.tenantSlug` is now generated at registration (deterministic slug, platform-global uniqueness with concurrency-safe suffix retry, immutable after provisioning) and persisted via Vendure CLI migration.
* The platform hostname `{tenantSlug}.{TENANT_PLATFORM_DOMAIN}` is seeded into the **existing** `DomainChannelResolverService` Redis mapping at registration, with update-path mapping recovery.
* `BbbOrganization.slug` is synchronized from `tenantSlug` via `TenantRegisteredEvent` → BBB provisioning listener (single consumer, async).
* **G2 hostname→Channel resolution passed** for Tenant A and Tenant B (distinct hostnames → distinct Channel tokens, via GraphQL registration only — no manual Redis/DB writes).
* Header correction made during G2: the Vendure channel-token header is `vendure-token` (the pre-B-2 snapshot above says `X-Vendure-Token`; the corrected name is authoritative and recorded in `integration-gaps-worklist.md`).

Sections 1–4 above remain as the historical pre-B-2 inspection snapshot and should not be read as the current state.
