## Key 3.7.3 behavior changes found & handled

### 1. GHSA-wr5h-x3x6-4h23 — login refused while `verificationToken` is pending

Native login now fails for an unverified user whenever the credential still
carries a pending `verificationToken` — **regardless of
`authOptions.requireVerification`** (which worked on 3.6.5). Symptom:
`Cannot return null for non-nullable field CurrentUser.id` on every
`registerNewTenant`-admin login (the flow intentionally creates the admin
unverified with a token — Phase 1.5).

**Fix (shared helper):**
`src/plugins/tenant-plugin/e2e/fixtures/verify-tenant-admin.ts`
— `verifyTenantAdminViaApi(server, shopClient, email)`:
READ the pending token (diagnostics-class read via
`NativeAuthenticationMethod` repo), then consume it through the public
Shop-API `verifyTenantAdmin` mutation (the application-API path production
uses). No DB writes. Called immediately after each `registerNewTenant`, while
`shopClient` still targets the default channel.

Wired into every suite that logs in as a `registerNewTenant` admin:
tenant-plugin (×2), bbb-channel-isolation (×2), marketplace (×2),
adr-046-self-serve (inside its `createTenant` helper), convergence (×1),
subscription-shop (×1), plus the two security suites (import moved to the new
fixture; signature simplified to `(server, shopClient, email)`).

### 2. `User.roles` is now a filtered `@ResolveField` (anti-enumeration, `@since 3.7.3`)

Core 3.7.3 resolves `User.roles` through `RoleService.getVisibleRoleIds`: a
viewer may only read a Role if they hold EVERY permission that Role grants on
every channel it is assigned to. A tenant-channel read-admin
(`[Authenticated, ReadAdministrator]`) therefore sees
`user.roles = []` for a tenant-admin row — expected hardening, not a bug.

**Test update:** tenant-plugin INV-016 "tenant A read-admin only sees
administrators in their own channel" now asserts
`tenantAdmin.user.roles` has length 0 (role details hidden) while the
administrator row itself stays visible (INV-016 channel scoping unchanged),
and keeps the BUG-030 nested-graph regression guard by asserting the
read-admin's OWN role (which passes the visibility filter) carries hydrated
`user.roles.channels` with the tenant channel code.

### 3. ES e2e indices were cleaned only in `afterAll` (best-effort)

The e2e Postgres schema is recreated per run (session PKs restart at 1) but
`e2e_marketplace_*` / `e2e_convergence_*` cleanup happened only at teardown —
a stale session doc from a previous run with a recycled PK satisfies
`waitFor()` immediately and carries the old `channelToken`
(order/state-dependent false failure, observed in marketplace Gate 1.5).

**Fix:** delete the suite's ES indices at the START of `beforeAll`
(idempotent setup; `assertInfrastructure()` already proves ES is up).
